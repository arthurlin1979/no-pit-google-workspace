# Google 整合維修與延伸紀錄：GP-T-01 至 GP-T-38

整理日期：2026-10-17。來源為維護者自有的 Google 整合踩坑表及同表更新紀錄，本檔未重新測試 Google、部署環境或資料庫。下列「已修」「已解」皆指原紀錄當時的狀態；Google 整合、內部程式、交付工具與外部設定分開標示，不將 38 項視為 38 個 Google 產品缺陷。外部規則未於本次重核。

<a id="gp-t-01"></a>
### GP-T-01 包裝 Drive 錯誤後，仍要留下可判斷的原因

- 類型：整合維修。
- 遇到的問題：Drive discovery 的例外經應用程式包裝後，後續流程缺少原始錯誤與 HTTP 狀態，難以區分可重試與應停止的失敗。
- 根因／處理：錯誤物件保留原始 `cause` 與 HTTP code，對外安全摘要另帶 `stage` 與 HTTP status，讓診斷與重試政策取得必要資訊。
- 原紀錄狀態與驗證界線：2026-10-12 記為程式已修；本列沒有獨立的線上部署讀回，本次亦未重測。

<a id="gp-t-02"></a>
### GP-T-02 403 要連同 Google reason 判讀，才能正確退避

- 類型：整合維修。
- 遇到的問題：把所有 HTTP 403 都當成永久拒絕，會讓實際遇到額度限制的同步立即停止。
- 根因／處理：重試政策納入 `rateLimitExceeded` 與 `userRateLimitExceeded`；403 帶這兩種 reason 時走退避，並套用到帳務、預約、照片、影片與單客 Sheet 等五個 runtime。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；這不代表所有 403 都可重試，也不代表本次已重驗各 runtime。

<a id="gp-t-03"></a>
### GP-T-03 多條 Sheets 同步要共用節流桶

- 類型：整合維修。
- 遇到的問題：各同步流程若各算自己的呼叫速度，同一使用者的整體流量仍可能一起撞上額度。
- 根因／處理：用共用 token bucket 約束 Sheets；原設定 burst 為 6、每秒補充、最長等待 30 秒，帳務與預約全量共用同一桶。Drive 保留既有 binary transport pacer，按 quota units 控速。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；參數是該整合的設定，不能當作 Google 對所有帳號的現行額度保證。

<a id="gp-t-04"></a>
### GP-T-04 排程錯開要放在應用程式的 offset 層

- 類型：整合維修。
- 遇到的問題：把 systemd timer 改成不同分鐘相位，反而讓應用程式永遠判定不到執行時間，形成無明顯錯誤的排程停擺。
- 根因／處理：應用程式原本依「台北分鐘 `% interval === offset`」判定；每五分鐘的外層觸發與它不一致。timer 回到 `0/5`，由應用程式在 15 分鐘週期內以 0、5、10 的 offset 錯開各同步。
- 原紀錄狀態與驗證界線：2026-10-12 第二版記為已修；這是內部排程整合問題。

<a id="gp-t-05"></a>
### GP-T-05 照片同步失敗先分類，再決定是否縮批

- 類型：整合維修。
- 遇到的問題：照片失敗若只有一個總數，無法看出是服務端錯誤、checksum、定位資訊，還是 metadata 問題，縮小批次也可能毫無作用。
- 根因／處理：新增照片失敗分類，分辨 `provider`、`checksum`、`locator`、`metadata` 等類別，並讓 sync run 計數保留類別，再據此決定後續縮批。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；分類能力不等於每類根因皆已修復，也沒有本次線上重測。

<a id="gp-t-06"></a>
### GP-T-06 資料表未就緒時擋開啟排程，仍要允許關閉

- 類型：資料契約。
- 遇到的問題：部署後若尚未具備同步需要的資料表，直接啟用排程會讓 worker 進入不可用路徑。
- 根因／處理：三組排程設定在「要開啟且資料表缺失」時回報 `GOOGLE_WORKSPACE_METADATA_UNAVAILABLE` 及所需 migration，要求先確認結構已套用；關閉排程不受 schema 缺件阻擋。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；這是啟用前的資料庫就緒檢查，不能取代實際 migration 與部署證據。

<a id="gp-t-07"></a>
### GP-T-07 OAuth 的發布狀態與應用程式驗證要分開確認

- 類型：外部設定待確認。
- 遇到的問題：原先擔心 OAuth 授權會受 Testing 模式的七天期限影響，卻尚未確認控制台狀態。
- 根因／處理：2026-10-14 人工讀回 `Publishing status=In production`、`User type=External`，原表因此排除 GP-45 的七天規則；另明確記錄當時選擇不送 Google App verification。
- 原紀錄狀態與驗證界線：原列已結案；發布為 Production 不等於已通過驗證。原表另提醒未驗證警示與終身 100 人 OAuth user cap，本次未重核外部規則。

<a id="gp-t-08"></a>
### GP-T-08 同一設定頁的同步區塊要用相同狀態語意

- 類型：整合維修。
- 遇到的問題：Google Workspace 設定頁的三個區塊若各自呈現狀態，使用者難以一致判讀哪些排程已開啟、上次何時完成。
- 根因／處理：抽出共用的同步狀態列，統一顯示開啟狀態與上次完成時間，讓相同資料在不同同步區塊具有相同語意。
- 原紀錄狀態與驗證界線：2026-10-12 記為 UI 程式已修；本列沒有提供各區塊部署後逐一操作的讀回，本次也未做畫面驗收。

<a id="gp-t-09"></a>
### GP-T-09 照片 ETA 要用有效樣本，並與待同步數量一致

- 類型：整合維修。
- 遇到的問題：大量照片分輪同步時，沒有可信的完成時間預估；樣本太短或時間過長，也容易呈現誤導的精確數字。
- 根因／處理：用最近一次成功照片 run 的速度推算；少於 60 秒不估，超過 10,080 分鐘只顯示約一週以上。ETA 與 UI 待同步數量使用同一份 pending。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；這是依歷史速度推估，後續另查出樣本秒數型別問題，見 GP-T-28。

<a id="gp-t-10"></a>
### GP-T-10 已知 Drive file ID 時，避免每次重新搜尋

- 類型：整合維修。
- 遇到的問題：每次依名稱或 marker 搜尋既有 Drive 檔案，增加查詢成本，也把查找結果變成同步的額外依賴。
- 根因／處理：客戶總表已有 Google file ID 時直接讀取該檔並驗證 marker，搜尋退為兜底與唯一性檢查。預約快照因寫入前檢查需求，刻意保留搜尋。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；原文最初同列兩個 runtime，更新已收斂範圍，不能宣稱所有 Drive 搜尋都已移除。

<a id="gp-t-11"></a>
### GP-T-11 根目標建立失敗要分出真正階段

- 類型：整合維修。
- 遇到的問題：歷史全量同步只留下 `ROOT_TARGET_FAILED`，無法從總碼判斷是根資料夾名稱、資源 ID 約束，還是 Sheet 格式設定失敗。
- 根因／處理：把 root 名稱、resource IDs constraint、`spreadsheet_format` 三個 stage 的實際原因納入失敗分類，避免不同問題全部落入同一個通用標籤。
- 原紀錄狀態與驗證界線：2026-10-12 記為分類程式已修；新增診斷不等於已逐筆重跑或修正所有歷史失敗。

<a id="gp-t-12"></a>
### GP-T-12 過期的同步 run 不應永久擋住 worker

- 類型：整合維修。
- 遇到的問題：同步 run 沒有持續 heartbeat 時，仍可能被視為有效工作，讓後續 worker 長期無法前進。
- 根因／處理：把過期判定抽成 30 分鐘的具名常數，SQL 由相同常數產生；狀態讀取回傳 `stale`，UI 顯示「視為卡住」，背景 worker 不再永久受它阻擋。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；它處理過期狀態，從未啟動的 run 為何失敗另見 GP-T-15、GP-T-16。

<a id="gp-t-13"></a>
### GP-T-13 增量同步要覆蓋所有來源，也要看見實體刪除

- 類型：資料契約。
- 遇到的問題：變動 gate 與 `workspace_updated_at` 的來源表集合不一致，新增消費可能被略過；hard-delete 又不會推進存活列的時間戳。
- 根因／處理：補齊 `GREATEST` 覆蓋集合，再記錄同一組來源列的 `source_fingerprint`，以「時間戳前進或指紋改變」挑選同步，並用結構測試鎖住集合一致。
- 原紀錄狀態與驗證界線：原表記程式已修，資料庫後續進度見 GP-T-38。指紋由第一次真實同步建立，不回填冒充已同步；基線之前的刪除無法追回。

<a id="gp-t-14"></a>
### GP-T-14 盤點工具寫錯正式資料庫名稱，查詢就失去依據

- 類型：內部交付。
- 遇到的問題：同步失敗盤點腳本的 `PROD_DATABASE` 常數使用了部署環境不存在的名稱，無法正確盤點目標正式庫。
- 根因／處理：核對真實資料庫名稱後修正常數，並同步更新守門測試，讓腳本與測試對準同一個實際目標。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；這是內部盤點工具的目標設定錯誤，不能歸因於 Google API，也不表示本次重新盤點過正式資料。

<a id="gp-t-15"></a>
### GP-T-15 從未啟動的 queued run，要留下真正失敗原因

- 類型：整合維修。
- 遇到的問題：大量 run 的 `started_at` 為空，卻反覆被下一輪改寫成 `STALE_RUN_RECOVERED`，掩蓋真正起因，另有 queued run 長期停住。
- 根因／處理：查明 worker 在開始 SQL 前就因 consumer marker 無法寫入而失敗；只對 `status=queued` 且 `started_at IS NULL` 的 run，以真正原因收束。
- 原紀錄狀態與驗證界線：2026-10-12 記程式已修；既有 414 筆歷史資料未修改。過期機制與寫入權限分見 GP-T-12、GP-T-16。

<a id="gp-t-16"></a>
### GP-T-16 systemd 唯讀沙箱要留下 worker 必要的寫入位置

- 類型：內部交付。
- 遇到的問題：worker unit 啟用 `ProtectSystem=strict`，卻沒有允許 origin-activation consumer 目錄寫入，導致啟動標記無法落地。
- 根因／處理：十個環境對應 unit 補上該 consumer 目錄的 `ReadWritePaths` 例外，並用結構測試檢查 unit 名稱與環境一致。
- 原紀錄狀態與驗證界線：2026-10-12 記為 repo 中的 unit 已修；原列明寫已安裝版本仍要重新安裝才生效，不能把 source 修正當成當時主機已更新。

<a id="gp-t-17"></a>
### GP-T-17 排程失敗摘要要能診斷，也要避免洩漏

- 類型：整合維修。
- 遇到的問題：worker 只輸出 `GOOGLE_WORKSPACE_SCHEDULED_SYNC_FAILED`，大量失敗的真因在 log 與資料庫摘要中都看不到。
- 根因／處理：改用白名單摘要，保留 `code`、`causeCode`、stage、持久化階段及 HTTP／Google status、reason 等診斷欄位；不直接輸出完整例外 message、路徑或憑證。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；安全摘要增加可觀察性，不能據此宣稱歷史失敗本身皆已解決。

<a id="gp-t-18"></a>
### GP-T-18 日報與預約快照的排程，要看實際觸發路徑

- 類型：內部交付。
- 遇到的問題：最初發現已安裝 unit 漂移、timer 停用，日報與快照缺少預期執行；但獨立 timer 的狀態不能單獨代表快照是否有跑。
- 根因／處理：更新 unit 後保留日報 timer；預約快照已由 daily-report bundle 同輪執行，刻意停用獨立快照 timer 避免雙跑。
- 原紀錄狀態與驗證界線：2026-10-16 原表結算，日報連續八個營業日 `readback_verified`、快照筆數不中斷。這是當時讀回，未在本次重驗；另見 GP-T-19。

<a id="gp-t-19"></a>
### GP-T-19 bundle 已包含快照，就不要再開第二個排程搶名額

- 類型：整合維修。
- 遇到的問題：日報 bundle 第一步會排入預約快照；獨立 timer 先成功後，同一天、同 kind 與 trigger 的第二筆被 `GOOGLE_WORKSPACE_SYNC_RUN_ACTIVE` 擋下，整個日報也失敗。
- 根因／處理：保留 daily-report timer，停用獨立預約快照 timer，讓 bundle 每天依序完成快照與日報，遵守每營業日一輪的閘門。
- 原紀錄狀態與驗證界線：2026-10-12 記為已修；當列主要記設定變更，後續持續執行證據見 GP-T-18。

<a id="gp-t-22"></a>
### GP-T-22 共用 main checkout 被占用時，先確認分支所有權

- 類型：內部交付。
- 遇到的問題：發布 preflight 要求 canonical checkout 位於乾淨的 main 且對齊遠端，但當時它被其他工作線使用，直接推 main 也被 receive gate 拒絕。

<a id="gp-t-23"></a>

- 根因／處理：當時改用最新 main 重跑 Dev、驗收與正式 readiness 鏈；若維持舊候選，必須在既有有效窗口完成，不能倒退 main 丟失其他工作。
- 原紀錄狀態與驗證界線：2026-10-12 記為已解；限制來自當時產出器，不是候選程式必然不相容。後續阻斷見 GP-T-24。

<a id="gp-t-24"></a>

<a id="gp-t-25"></a>
### GP-T-25 接受通用 Dev proof 時，仍要完整驗證其綁定

- 類型：內部交付。

<a id="gp-t-26"></a>
### GP-T-26 SQL 字串裡的註解，要遵守 SQL 語法

- 類型：資料契約。
- 遇到的問題：設定 API 回 400，原因藏在很下層的 SQL：template literal 內寫了 TypeScript 的 `//` 註解，PostgreSQL 將內容當運算式解析而報錯。
- 根因／處理：改用 `--` 行註解，並掃描 SQL template 的 `//` 開頭行。原契約測試使用 fake query layer，不會真正 parse SQL，因此沒有攔到。
- 原紀錄狀態與驗證界線：2026-10-12 原表記修前可抓一處、修後零處，90 項測試通過；當時僅 Dev 含此錯誤，不能寫成正式環境事故。

<a id="gp-t-27"></a>
### GP-T-27 有型別相依的 SDK，要同步更新版本

- 類型：內部交付。
- 遇到的問題：只更新頂層 `ai`，讓 `@ai-sdk/react` 又安裝另一版 `ai`，兩份 `UIMessage` 的 metadata 型別不一致，導致新候選 build 型別檢查失敗。
- 根因／處理：把 `@ai-sdk/react` 更新到內部相依版本與頂層一致，移除 nested 重複依賴，並沿用 exact pin，避免 lockfile 與 manifest 不一致。
- 原紀錄狀態與驗證界線：2026-10-13 記 `npm ci` 與 typecheck 通過；當時既有 Dev、Prod 在問題更新之前，沒有受影響。這是交付相依問題。

<a id="gp-t-28"></a>
### GP-T-28 照片耗時可有小數，不能當列數驗證

- 類型：資料契約。
- 遇到的問題：ETA SQL 的 `EXTRACT(EPOCH ...)::numeric` 產出小數秒，卻被要求非負整數的 `normalizeCount` 拒絕，讓整個同步狀態 API 回 400。
- 根因／處理：耗時改用 `normalizeSampleSeconds`，接受有限非負數再四捨五入；負數與無限值仍拒絕，照片張數仍維持整數計數檢查。
- 原紀錄狀態與驗證界線：2026-10-13 記回歸測試與 ETA 測試共 12 項通過；與 GP-T-26 症狀相同但根因不同，不能共用同一修法。

<a id="gp-t-29"></a>
### GP-T-29 Access 放行機器，不代表應用程式收到登入身分

- 類型：驗證紀錄。
- 遇到的問題：Ops 瀏覽器驗收需要可驗證的 JWT actor；無憑證回 302，原設定下帶 service token 雖穿過 Access，應用程式仍回 403。
- 根因／處理：該次發布以本人確認的人工 acceptance 完成；另以有效、綁定候選且未改 Access 驗證表面的 Ops 安裝讀回替代 browser check，policy 已實測生效。
- 原紀錄狀態與驗證界線：原列仍標未解：尚無帶該替代證據的完整 terminal 驗收讀回，待 App／Ops 同批交付。人工接受整批 checks 也不等於各項自動通過，見 GP-T-35。

<a id="gp-t-30"></a>
### GP-T-30 socket 已回覆拒絕，暫存 unit 不該再假裝程式崩潰

- 類型：內部交付。
- 遇到的問題：Ops rebuild 暫存 unit 大量留在 failed，journal 卻只有 systemd 狀態；具名 rejection 已透過 socket 回覆，CLI 仍以 exit 1 結束。
- 根因／處理：已完成契約回應的拒絕改用 exit 0，非預期且無回應的例外才 exit 1；stderr 增加白名單診斷，限制 request／action 格式以防偽造 log。
- 原紀錄狀態與驗證界線：2026-10-13 記初修及清理完成，但隨即發現 health 回應沒有 `ok`，初修仍有洞；後續由 GP-T-40 承接，不能只看「已修」。

<a id="gp-t-31"></a>
### GP-T-31 修一個 Ops 暫存 runner，還要核對同類出口

- 類型：內部交付。
- 遇到的問題：rebuild runner 的 failed 噪音清理後，又發現 slot-reset runner 有相同 `Accept=yes` 暫存實例累積，journal 也缺乏真正原因。
- 根因／處理：對具名拒絕與非預期例外區分結構化回應、退出碼與安全診斷，並核對全部同類 failed units；不能從一條 runner 已修推論另一條也完成。
- 原紀錄狀態與驗證界線：2026-10-15 原表記新版本已安裝，兩次 slot 重建後相關 failed units 為零、三層讀回通過；本次未重驗。

<a id="gp-t-32"></a>
### GP-T-32 測試 DDL 若照錯誤假設編寫，綠燈也會掩護壞 SQL

- 類型：資料契約。
- 遇到的問題：快照 SQL 引用不存在的 `visit.visit_id`，且把 uuid 直接交給 `string_agg`；合成測試卻自行補出欄位、把 uuid 寫成 text，錯誤全部變綠。
- 根因／處理：修正關聯鍵並顯式 cast，機械解析 `alias.column`，對照權威 baseline 加 migrations；隔離 DDL 使用權威或實測結構，塞回舊錯必須變紅。
- 原紀錄狀態與驗證界線：2026-10-13 記為已修；同表後續更新記正式 release 的實際 SQL 已可 `EXPLAIN`，不能沿用舊 release 宣稱仍待緊急拆雷。

<a id="gp-t-33"></a>
### GP-T-33 未結算的 Preview locator，可能擋住已成功的新部署

- 類型：內部交付。
- 遇到的問題：舊 `initializing` locator 綁定過去部署，新部署雖已有 applied proof，continuation 仍要求舊 owner；另一條出口又要求舊 locator 自帶不存在的 finalized receipt。
- 根因／處理：原列列出以受支援 proof 接納較新部署、連結未完成 locator、受控結算等出口；禁止手刪 active locator 或改 hash 偽造通過。
- 原紀錄狀態與驗證界線：2026-10-13 記程式已修，但本列未說明最後採哪一出口及完整讀回；公開說明不能補造這些細節。

<a id="gp-t-34"></a>
### GP-T-34 驗收讀取與實際注入的憑證組，必須語意一致

- 類型：內部交付。
- 遇到的問題：smoke 讀 release 組，環境卻只有另一組鍵；即使已設定憑證，runner 也不一定取得正確的機器身分來源。
- 根因／處理：依驗收政策改讀 machine 組；直接 env 優先，缺值才解析受信任 E2E env 檔，避免仰賴 launcher 透傳。不能任意互換 machine、release、slot 的語意。
- 原紀錄狀態與驗證界線：2026-10-14 記 12 項契約測試通過，原列仍要求安裝含最終修正的版本後完成實際 smoke 讀回，不能把測試當三層驗收。

<a id="gp-t-35"></a>
### GP-T-35 共用判準修好後，還要確認 Preview 真能取得證據

- 類型：驗證紀錄。
- 遇到的問題：共用 Dev 可用 Ops readback 替代 browser check，Preview 卻仍要求它；初步歸因為兩條 policy 路徑不一致。
- 根因／處理：共用 predicate 補 ancestry 正向證據後，真實 Dev policy 已可生成 schema 9；但 Preview 只收尚未進 main 的候選，新分支的證據卻要求已進 main，形成條件互斥。
- 原紀錄狀態與驗證界線：原表狀態稱已解，同表末段仍記 Preview schema 10 無端到端證據，並停止繼續改比較邏輯。應保留這項差異，不能宣稱兩路均已實測通過。

<a id="gp-t-36"></a>
### GP-T-36 Dev 讀得到預設值，不表示寫入結構已備妥

- 類型：資料契約。
- 遇到的問題：Dev 與正式庫的 migration 漂移，讀取用 JSON 加預設值掩蓋缺欄，設定寫入的 `EXPLAIN` 卻直接報欄位不存在。
- 根因／處理：把 migrations 的 `ADD COLUMN`、`CREATE TABLE` 展開為存在性查詢，逐庫比對；後續以正式庫為基準重建測試槽，消除這次結構落差。
- 原紀錄狀態與驗證界線：2026-10-14 原表讀回三庫所需欄位與設定表一致，這次症狀已消除；沒有套用歷史表的另項問題由 GP-T-37 承接。

<a id="gp-t-37"></a>
### GP-T-37 migration 要留下可核對的套用歷史

- 類型：資料契約。
- 遇到的問題：沒有套用紀錄表時，無法直接回答各庫執行過哪些 migration，readiness 只能反覆從欄位存在性推回，漂移容易長期隱藏。
- 根因／處理：最後實作的歷史表以 `filename`、`sha256`、environment、套用時間、actor、operation_id 記錄；新 runner 成功後自我登記，既有項目依正向證據補登。
- 原紀錄狀態與驗證界線：2026-10-16 原表記正式與共用 Dev 表已存在、正式讀回 17 列；舊快照槽未必有表，需重建，不能推論所有槽位皆已一致。

<a id="gp-t-38"></a>
### GP-T-38 先備妥新欄位，再上讀它的程式；Dev 限定要有後端閘門

- 類型：資料契約。
- 遇到的問題：原計劃把附加欄位的 migration 排在新程式之後，會造成缺欄窗口；另有單客 route 的後端同時接受 Dev、Prod，當時已無 UI 呼叫者。
- 根因／處理：以唯讀 `EXPLAIN` 確認依賴，先套向後相容的 nullable 欄位；UI 文字無法取代環境閘門。相關套用器的 Parse-before-CASE 問題見 GP-107。
- 原紀錄狀態與驗證界線：2026-10-13 記四階段套用通過、無回填且既有 mapping 摘要不變；是否收緊為 Dev-only 仍是產品決策，不可寫成已修。
