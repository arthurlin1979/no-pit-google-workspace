# Google 整合主項紀錄

本檔依私人來源表的原章節，逐條整理 108 個 GP 主項。編號保留原樣，因此 GP-106、GP-107、GP-108 不按數字排序。這些條目包含整合經驗、內部契約、交付問題及外部參考，不能合計成 108 個獨立 Google 缺陷或實驗。

來源僅限原表。本次只整理文字，沒有重新檢查程式碼、外部文件或線上環境，也沒有執行修復。文中的數字、設定與結果都是原表的歷史記載，未在本次重核；內部常數不代表 Google 上限，外部參考也不構成 Google 現行保證。原表提及的修復，只代表當時記載的處理，不代表目前已部署或仍有效。

## 一、連線時間與逾時

<a id="gp-01"></a>
### GP-01 大型讀寫先碰到自己的請求逾時

- 類型：內部參數與契約。
- 紀錄重點：原記載單次請求預設 60 秒，允許範圍為 1 至 60 秒；大表或大量讀回可能先被內部計時器中止。
- 處理方式：把工作拆成小請求，避免只拉長等待時間。
- 驗證與界線：這是歷史內部設定，未本次重核，也不是 Google 的處理時間保證。

<a id="gp-02"></a>
### GP-02 單次請求過關仍可能耗盡整體時間

- 類型：內部參數與契約。
- 紀錄重點：原記載整體工作預設 180 秒，允許 30 至 300 秒；單一對象的完整流程可能被整體期限中止。
- 處理方式：控制整體工作量，較長流程拆批或改由背景工作接續。
- 驗證與界線：數字是歷史內部預算，未本次重核；個別請求成功不等於整體工作完成。

<a id="gp-03"></a>
### GP-03 取消訊號要涵蓋請求與整體工作

- 類型：內部參數與契約。
- 紀錄重點：原表以 `AbortSignal.any` 合併兩層取消訊號；只接一層會讓整體逾時後，進行中的請求繼續執行。
- 處理方式：新增呼叫點也要傳入合併訊號，避免使用未綁定的 `fetch`。
- 驗證與界線：這是來源記載的設計契約，本次沒有重跑取消或逾時測試。

<a id="gp-04"></a>
### GP-04 擴大授權也要檢查 token 回應容量

- 類型：內部參數與契約。
- 紀錄重點：原記載 `TOKEN_RESPONSE_MAX_BYTES` 為 64 KB；新增 scope 後，回應可能超過程式接受的容量。
- 處理方式：調整授權範圍時，一併檢查回應大小與解析方式。
- 驗證與界線：這是歷史內部防護值，未本次重核；與 GP-05 相關，不能當作 Google 回應上限。

<a id="gp-05"></a>
### GP-05 userinfo 與 token 的容量要分開管理

- 類型：內部參數與契約。
- 紀錄重點：原記載 `USERINFO_RESPONSE_MAX_BYTES` 為 32 KB；增加 OIDC claim 可能使回應被截斷，造成 JSON 驗證失敗。
- 處理方式：更動 scope 或 claim 時，同時檢查 userinfo 與 token 兩條讀取路徑。
- 驗證與界線：數字是歷史內部設定，未本次重核；關聯 GP-04，兩者不能混成一個上限。

<a id="gp-06"></a>
### GP-06 大表寫入要按位元組分批

- 類型：內部參數與契約。
- 紀錄重點：原記載 `FULL_VALUES_REQUEST_MAX_BYTES` 為 1,800,000；超大的 values 請求會碰到內部容量限制。
- 處理方式：依內容位元組估算批次，再分塊寫入。
- 驗證與界線：這是歷史內部門檻，未本次重核，不是 Google 硬上限；GP-102 是同一契約的延伸。

<a id="gp-07"></a>
### GP-07 大範圍讀回可能被內部容量截斷

- 類型：內部參數與契約。
- 紀錄重點：原記載讀取回應上限為 256 KB；一次讀太大的 range，可能把截斷誤認為資料遺失。
- 處理方式：縮小讀取範圍，分段讀回並確認解析完整。
- 驗證與界線：這是歷史內部設定，未本次重核；不能由不完整回應推論 Google 已刪除資料。

<a id="gp-08"></a>
### GP-08 包裝錯誤時要留下真正原因

- 類型：整合案例。
- 紀錄重點：來源記載曾把 refresh、scope、網路與逾時都包成 `GOOGLE_WORKSPACE_DRIVE_DISCOVERY_FAILED`，使故障難以區分。
- 處理方式：保留原始 cause 與 HTTP 狀態，讓後續診斷能分辨失敗層次。
- 驗證與界線：本次未重現；某次重試成功，不能倒推過去失敗的原因。

<a id="gp-09"></a>
### GP-09 遠端操作逾時後先查原操作

- 類型：交付與驗證。
- 紀錄重點：等待逾時或沒有最終結果，不足以證明遠端操作未執行；再次下發可能造成重複執行。
- 處理方式：用原操作識別資訊查詢 `status`，直到取得可判讀的終態。
- 驗證與界線：`ops_operation_pending` 是來源記載的待讀回狀態；本次沒有操作遠端系統，也不提供重播許可。

<a id="gp-10"></a>
### GP-10 登入導向不能直接判成程式故障

- 類型：交付與驗證。
- 紀錄重點：原表曾觀察匿名或無效憑證取得 302，已登入請求取得 200；兩者經過的存取條件不同。
- 處理方式：用持有授權狀態的請求讀回結果，先辨認導向目的。
- 驗證與界線：這是歷史觀察，未本次重測；302 單獨不能證明程式故障，200 也不等於完整驗收。

## 二、重試次數與等待時間

<a id="gp-11"></a>
### GP-11 重試時間也會吃掉排程預算

- 類型：內部參數與契約。
- 紀錄重點：原記載系統性重試依序等待 1、2、4、8、16、32 秒；重試等待會佔用同一輪的工作時間。
- 處理方式：比較總等待與排程間隔，超過合理預算時交由下一輪接續。
- 驗證與界線：數字是歷史內部設定，未本次重核；不能據此宣稱任何外部故障都可恢復。

<a id="gp-12"></a>
### GP-12 寫入重試較少時要留下失敗階段

- 類型：內部參數與契約。
- 紀錄重點：原記載 values 寫入等待 1、2 秒後重試，預算少於其他讀取或系統性重試。
- 處理方式：把失敗 stage 記清楚，讓下一輪知道從何處接續，避免整段盲目重做。
- 驗證與界線：這是歷史內部策略，未本次重核；接續仍須確認前次寫入結果與冪等條件。

<a id="gp-13"></a>
### GP-13 寫入後立即查不到不一定是失敗

- 類型：內部參數與契約。
- 紀錄重點：原記載最終讀回最多嘗試 6 次，等待參數為 3 秒，用來容納外部可見性延遲。
- 處理方式：先完成有界讀回，再判斷是否需要恢復，避免立即回滾或重寫。
- 驗證與界線：這是歷史內部容忍窗口，未本次重核；超出窗口只能表示尚未證明成功。

<a id="gp-14"></a>
### GP-14 大影片不能只靠重試同一個 chunk

- 類型：內部參數與契約。
- 紀錄重點：原記載每個影片 chunk 的重試上限為 2 次；大型上傳中斷需要更完整的恢復機制。
- 處理方式：保留 resumable session，依可續傳狀態恢復，而非無限重傳單塊。
- 驗證與界線：重試次數是歷史內部設定，未本次重核；本次沒有驗證 session 恢復成功率。

<a id="gp-15"></a>
### GP-15 是否重試要一起看狀態與 reason

- 類型：整合案例。
- 紀錄重點：原表的內部策略若把所有 403 都視為不可重試，會漏掉 `rateLimitExceeded` 與 `userRateLimitExceeded`。
- 處理方式：同時解析 HTTP 狀態與錯誤 reason，再決定退避或停止。
- 驗證與界線：來源混合實作與官方參考，未本次重核；關聯 GP-36，不能只憑單一狀態碼判斷。

<a id="gp-16"></a>
### GP-16 OAuth 失敗後要重新開始授權

- 類型：內部參數與契約。
- 紀錄重點：授權碼與 state 具一次性；來源記載重播舊 callback 會遇到 `GOOGLE_WORKSPACE_OAUTH_STATE_INVALID`。
- 處理方式：重新發起連接流程，取得新的 state 與授權碼。
- 驗證與界線：這是原表的授權流程契約，本次未測登入；重新開始不代表可以跨瀏覽器重用原 session。

<a id="gp-17"></a>
### GP-17 排程分輪補齊資料

- 類型：內部參數與契約。
- 紀錄重點：原記載照片、影片與同步 timer 每 5 分鐘觸發；資料會逐輪處理，不保證一輪完成全量。
- 處理方式：在說明與介面明確標示待同步量，以及逐輪補到歸零的行為。
- 驗證與界線：頻率是歷史內部配置，未本次重核；觸發 timer 也不等於每次都產生有效工作。

<a id="gp-18"></a>
### GP-18 凌晨排程可能集中競爭額度

- 類型：內部參數與契約。
- 紀錄重點：原表列有相近時間的每日快照、每日報表與定期交付工作，提醒集中觸發會增加請求壓力。
- 處理方式：檢查各排程依賴，錯開時間或共用節流機制。
- 驗證與界線：這是歷史排程配置與風險紀錄，未本次重核；不能從時間相近就認定已發生限流。

## 三、批次大小與併發

<a id="gp-19"></a>
### GP-19 批次大不代表完成得快

- 類型：內部參數與契約。
- 紀錄重點：原記載單客 Sheet 穩定批次為 100 個對象；批次帶來的請求數仍會受使用者額度約束。
- 處理方式：把單客請求量與額度一起估算，避免只增加批次數。
- 驗證與界線：100 是歷史內部參數，未本次重核；額度參考見 GP-40、GP-41，併發見 GP-20。

<a id="gp-20"></a>
### GP-20 併發要與單一使用者額度一起計算

- 類型：內部參數與契約。
- 紀錄重點：原記載單客 Sheet 併發為 4；提升併發會讓同一時間的請求更集中。
- 處理方式：先估算每個對象的讀寫次數與使用者請求速率，再調整併發。
- 驗證與界線：數字是歷史內部設定，未本次重核；關聯 GP-19、GP-40、GP-41，不能當成通用安全值。

<a id="gp-21"></a>
### GP-21 零延遲會放大瞬間請求量

- 類型：內部參數與契約。
- 紀錄重點：原記載對象間延遲為 0，與並行處理搭配時會形成短時間大量請求。
- 處理方式：碰到限流時先評估節流與請求分布，再決定是否改批次。
- 驗證與界線：這是歷史內部配置，未本次重核；原表沒有證明只改某一參數即可解決所有限流。

<a id="gp-22"></a>
### GP-22 證明回填的批次有自己的預算

- 類型：內部參數與契約。
- 紀錄重點：原記載照片輸出證明回填預設批次 25、上限 100；保守批次在大量資料下可能耗時。
- 處理方式：如需上調，先計算回填路徑實際會發出的請求量。
- 驗證與界線：數字是歷史內部設定，未本次重核；較大批次的穩定性不能由設定上限自行推出。

<a id="gp-23"></a>
### GP-23 開發環境的併發結果不能直接外推

- 類型：整合案例。
- 紀錄重點：原表記載照片併發由 3 調到 4、再到 5，當時開發測試未觀察到 quota 或 429。
- 處理方式：用同尺寸照片批次比較時間，再另行評估正式環境變更。
- 驗證與界線：這是歷史開發實驗，未本次重測，也未由該筆證明正式環境可採相同配置。

<a id="gp-24"></a>
### GP-24 單輪照片量太大時要先分類失敗

- 類型：整合案例。
- 紀錄重點：原表記載單輪 5,000 張曾有 2,644 張成功、2,356 張失敗；可選批次與輪次上限屬內部設計，不是 Google 官方限制。
- 處理方式：當時先縮到每輪 500 張，並依 failed reason 分類，避免持續放大未釐清的失敗。
- 驗證與界線：本次未重跑原批次；成功與失敗混合不能直接歸因於 Google 額度，也不能據此保證縮批有效。

- 驗證與界線：數字與樣本都是歷史記載，未本次重核，不能外推到其他照片集合。

## 五、Google 官方額度與限制

<a id="gp-33"></a>
### GP-33 專案額度要依計量單位理解

- 類型：外部規則參考。
